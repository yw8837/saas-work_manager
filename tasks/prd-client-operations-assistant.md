# 일감체크 고객 소통·수정 요청 고도화 기획

2026-10-25 · 기획 및 검증 설계 · 제품 구현·배포 변경 없음

> 최신 사업·조사·예산 기준은 [실행기획서](../docs/strategy/일감체크_실행기획서.md)를 따른다. 아래의 기본 접수 요구사항은 보존하되, 카카오톡 채널은 사업 타깃 전체가 아닌 기술 파일럿 조건이다. 인터뷰는 마켓 중심 6명·직접 수주 중심 6명 목표로 통합했고, 효과 판정은 초기 설정 전액을 포함한 2주 절대 순절감과 상대 절감률을 함께 쓴다. 미구현 기능의 구현 승인으로 읽지 않는다.

## 1. 먼저 내릴 결정

**‘확인·수락한 요청만 작업과 수정 회차에 반영’하는 흐름은 기본 기능으로 정리한다. 이를 핵심 차별점으로 내세우지 않는다.**

최신 핵심 가치 후보는 [반복 고객응대 핵심 가치 재검토](../docs/research/2026-10-25-고객응대-핵심가치-재검토.md)의 **주문별 반복 고객응대 처리**다. [고객 지연 후 재개 일정 조율](./prd-client-delay-reagreement.md)은 사용자 판단에 따라 보조 후보로 내렸다. 아래 문서는 기본 접수 흐름의 요구사항이며, 새 후보는 **미구현·미검증 제안**이다. 구현 승인이나 독점 기능 확인을 뜻하지 않는다.

새 후보의 제한적 자동 사실 안내는 별도 설계·승인 대상이다. 이 PRD의 AI 초안·사람 승인 단계나 현재 운영 발송 정책이 이미 바뀐 것은 아니다. Notion Custom Agents·채널톡 ALF·OnBrio의 유사 기능과 비교해 설정·검수까지 포함한 순절감 시간을 검증한다.

**채널 선행 조건:** 개인 카카오톡 대화 수신·답장의 공식 API는 제공되지 않으며, 크몽의 외부 메시지 API는 공개 조사에서 확인하지 못했다. 최신 후보는 기존 카카오톡 채널 이용 제작자의 ‘대화→작업 연결’·‘작업→같은 채널 안내’로 범위를 좁혀 검증하는 안이다. 타깃 변경 승인·연동 구현·실제 왕복 테스트는 별도다. 고객 링크 강제와 복사·붙여넣기를 자동화 성과로 계산하지 않는다. 자세한 근거·제약·SCQA는 위 재검토 문서 6·10절을 따른다.

노션이나 슬랙을 통째로 대체하지 않는다. 정해진 작업을 반복 판매하는 사람이 고객 요청을 다시 정리하고, 수정 횟수를 계산하고, 진행 조건을 반복 설명하는 일을 줄이는 것이 목적이다.

고객 요청 → 작업자 내용 확인 → 진행 수락 → 수정 회차 차감·진행 상태 반영.

‘확인’과 ‘수락’을 불필요하게 두 버튼으로 나누지 않는다. 요청을 읽은 뒤 **‘수정 진행 · 1회 사용’**을 누르는 한 번의 확정으로 처리한다. 단순히 읽거나 접수됐다는 사실만으로 차감하지 않는다.

### 멘토에게 설명하는 SCQA

아래 표는 기본 수정 접수 기능의 설명이다. 최신 제품 가치 제안의 SCQA는 [반복 고객응대 재검토 10절](../docs/research/2026-10-25-고객응대-핵심가치-재검토.md)을 사용한다. 기본 기능 설명을 전체 제품의 새 핵심 차별점으로 바꾸어 읽지 않는다.

| 구조 | 설명 |
|---|---|
| S · 상황 | 홈페이지·디자인·영상처럼 작업 범위와 수정 조건을 정해 반복 판매하는 제작자가 있다. 크몽뿐 아니라 자사몰·전문가 플랫폼·소개 거래에도 같은 형태가 존재한다. |
| C · 문제 | 고객은 자료·질문·수정을 따로 보내고 제작자는 이를 작업으로 정리한다. 추가 작업인지, 남은 수정인지, 언제 해줄 수 있는지 다시 설명해야 한다. 여러 일감이 겹치면 이 관리 시간이 늘 수 있다. |
| Q · 질문 | 제작자에게 매번 조건 입력과 도구 설정을 시키지 않고, 고객 요청을 어떻게 처리 가능한 작업으로 바꿀 것인가? |
| A · 답 | 한 번 저장한 패키지 조건을 새 일감에 적용하고, 작업자가 확인·수락한 수정만 회차와 진행 상태에 반영한다. 범위를 넘으면 추가 조건을 먼저 합의한다. 이후 자료 요청·진행 안내로 같은 흐름을 확장한다. |

AI 사용으로 생산성이 높아져 실제 동시 수주량도 늘었는지는 **시장 가설**이다. 제품을 설명하기 위해 사실로 단정하지 않는다. 경쟁 제품에 비슷한 기능이 있으므로 ‘세계 유일’보다 설정·운영 시간을 얼마나 줄이는지로 설득한다.

## 3. 왜 이 문제부터 푸는가

[경쟁 제품·고객 불만 근거표](../docs/research/2026-10-25-경쟁제품과-고객불만.md)에 출처와 반례를 함께 기록했다.

- 국내 경험담: 작은 수정 누적·늦은 피드백·작업자 요청 누락.
- 해외 사용자 토론: 포털 미사용, 이메일 재입력, 접수와 실제 작업 약속의 혼동.
- 경쟁 제품: Notion은 폼·자동화뿐 아니라 Custom Agents의 데이터 조회·메시지 전송, Slack은 워크플로와 연동, Bonsai는 고객 포털, Scopepin은 수정 회차와 범위 초과 승인까지 제공한다. 최신 AI 응대 반례와 한계는 위 재검토 문서를 함께 읽는다.

따라서 **알림, 고객 링크, 수정 카운터 하나만으로는 차별성을 주장하기 어렵다.** 우리 타깃이 패키지 한 번 설정 후 별도 자동화 구축 없이 짧게 처리할 수 있는지가 승부다. 독점성은 미입증이며, 지불 의사는 실험으로 판단한다.

## 4. 요청을 확인하고 수락하는 규칙

### 4.1 고객 화면

- 고객은 자기 일감의 링크에서 요청 내용과 참고 자료 링크를 보낸다. 전체 관리도구 가입은 요구하지 않는 방향이다.
- 접수 직후 ‘요청이 전달됐습니다. 작업자가 확인한 뒤 진행 여부를 안내합니다’라고 표시한다.
- 접수 확인을 ‘작업 시작’ 또는 ‘무료 수정 승인’으로 표현하지 않는다.
- 현재 일감의 합의 범위·남은 수정·진행 여부만 공개한다. 다른 고객, 내부 원가, 내부 메모는 표시하지 않는다.

### 4.2 작업자 화면

| 판단 | 행동 | 차감 | 고객 안내 |
|---|---|---|---|
| 합의한 범위의 수정, 잔여 회차 있음 | 수정 진행 · 1회 사용 | 확정된 회차 1회 | 이번에 반영할 항목·수정 후 잔여·예정 안내 |
| 단순 질문·자료 보충 | 답변 또는 자료 확인 | 0 | 답변·자료 접수 |
| 작업자가 빠뜨리거나 잘못 반영한 내용 | 오류 보완으로 진행 | 0 | 보완 항목·예정 안내 |
| 내용이 애매함 | 설명 요청 | 0 | 확인할 질문 한 가지 또는 필요한 자료 |
| 범위 초과·잔여 없음 | 추가 작업 협의 | 합의 전 0 | 추가 범위·금액·납기 조건 제안 |
| 진행 불가·철회 | 사유와 함께 종료 | 0 | 불가·철회 결과 |

수락과 차감은 원자적 처리, 즉 둘 다 성공하거나 둘 다 실패하게 만든다. 네트워크 재시도·더블클릭으로 두 번 차감하지 않는다. 잘못 수락한 경우 이력을 삭제하지 않고 취소 이벤트로 되돌린다.

### 4.3 메시지 개수와 수정 회차는 다르다

이번 고도화의 기본 검증안은 **같은 확정 수정 묶음의 보충 의견을 새 회차로 자동 차감하지 않는 것**이다. 기존에 ‘요청 1건=수정 1회’로 계약한 고객의 조건까지 소급해서 바꾸지 않는다.

예시: 고객이 색상·문구·여백 요청을 세 번 나눠 보냈어도, 작업자가 이를 하나의 수정 묶음으로 확정하고 고객에게 그 목록을 안내했다면 1회로 관리한다. 확정 이후 새 요청은 보충인지 새 회차인지 작업자가 판단하고 고객에게 알린다.

요청·회차 정책은 패키지에 한 번 저장하고 주문 시 복사한다. 새 일감마다 같은 약관을 다시 입력하지 않는다. AI는 분류·문구 초안만 제안하고 금액·납기·차감·발송을 임의 확정하지 않는다.

## 5. 확장성: 채널보다 작업 형태

**‘크몽 판매자’가 아니라 ‘범위가 반복되는 서비스를 판매하고 여러 고객 일을 동시에 진행하는 제작자’가 기준이다.** 최초 검증은 1인 운영자, 다음 검증은 같은 방식으로 일하는 소규모 제작팀이다. 팀 권한·분배 기능은 현재 지원으로 표현하지 않는다.

| 순서 | 대상·진입 경로 | 현재 사업과의 접점 | 확인할 점 |
|---|---|---|---|
| 1 | 홈페이지·디자인·영상의 반복 외주, 크몽·소개·자사 사이트 | 기간·할 일·수정 조건 재사용 | 동시 일감 수, 소통 빈도, 현재 관리 시간 |
| 2 | 재능아지트·재능넷·숨고마켓의 조건 명시 상품 | 판매 채널만 달라지고 같은 패키지 재사용 가능 | 각 판매자의 실제 활동·범위·수정 조건. 플랫폼 전체를 패키지 시장으로 가정하지 않음 |
| 3 | 카페24·아임웹 전문가, 쇼핑몰 제작·상세페이지·짧은 광고 영상 업체 | 기업 고객에게도 반복 결과물 판매 | 기업형 제작사의 문제와 의사결정자 확인. 업체 수를 유료 고객 수로 환산하지 않음 |
| 4 | 반복 제작을 받는 소규모 스튜디오·에이전시 | 담당자·공통 고객 소통·다건 관리 | 팀 권한·감사 기록·가격 검증 후 진입. 대기업 ERP는 제외 |

실물 사례: [카페24 엑스퍼트의 디스벨로 상품](https://experts.cafe24.com/client/products/1108)은 10초 영상 1편, 스토리보드 승인 후 5일, 스토리보드·편집 각 1회 수정처럼 조건을 명시한다. **기업에도 반복 범위·단계별 수정 조건이 있다는 근거**이지, 해당 업체의 불만·인원·구매 의사를 확인한 것은 아니다.

추가 근거: [재능아지트 등급형 디자인 상품](https://www.skillagit.com/product/view.php?idx=13872), [아임웹 전문가](https://www.imweb.me/expert), [Fiverr 패키지](https://help.fiverr.com/hc/en-us/articles/360010559138-Creating-and-managing-Gig-packages), [Upwork Project Catalog](https://support.upwork.com/hc/en-us/articles/360057397533-How-to-create-a-project-in-Project-Catalog).

Fiverr·Upwork는 해외에도 작업 형태가 있다는 근거다. 즉시 해외 진출·주문 API 연동·해외 매출 가능성을 검증한 것은 아니다. 플랫폼 결제·소통 규정을 우회하지 않는다.

| 문제 인터뷰 | 제작자 12명, 그중 크몽 외 수주 경험자 4명 이상. 최근 실제 사례를 개인정보 가린 기록으로 확인 | 반복되는 문제가 특정 업종·작업 형태에서 확인되는지. 면담 수만으로 수요 검증 완료 처리 금지 |
| 사용 관찰 | 6명 × 각 3개 일감, 총 18개 일감 관찰 목표. 사용자 안에서 반복 측정 | 개별 사용자 기준 관리 시간이 줄어드는지. 일감 18개를 독립 고객 18명으로 계산하지 않음 |
| 기존 도구 비교 | 기존 메신저·엑셀/Notion 흐름과 같은 요청 시나리오 비교. Scopepin도 공개 체험 범위에서 비교 | 초기 설정 시간과 반복 사용 시간을 따로 기록. 서툰 비교군을 만들어 유리하게 측정하지 않음 |
| 핵심 효과 | 요청 확인·분류·기록·회차 정리·고객 안내에 걸린 능동 작업 시간 | 반복 관리 시간 중앙값 30% 감소를 가설로 시험. 실패하면 기능 추가보다 흐름 재설계 |
| 안전성 | 중복 차감·오류 수정 차감·무승인 비용/납기 변경·잘못된 수신자 발송 | 자동 회귀 시나리오 0건, 파일럿 사고 발생 시 원인 수정 전 확대 중단 |
| 사용성 | 일감 등록·요청 수락 클릭 수, 고객 재문의, 링크 이탈 | 2번째 이후 새 일감은 기존 4필드 범위 유지. 소통 단계가 늘어났다면 효과에서 차감 |
| 가격 | 동일 기능 설명 후 월 14,900원 이용 의사와 이유, 실제 결제 준비 후 유료 전환 | 의향·예약·실제 결제 구분. 현재 결제 기능 미구현 상태에서 매출로 기록 금지 |

필요 모집 수 = 목표 참여자 ÷ 회신율 ÷ 적격률 ÷ 참여 동의율. 예를 들어 6명 ÷ 20% ÷ 50% ÷ 60% = 100명이다. **각 비율은 계산 예시일 뿐 실제 예상 회신율이 아니다.** 소규모 선행 모집에서 비율을 측정한 뒤 규모를 조정한다. 연락·설문 발송은 별도 승인 후 진행한다.

## 7. 로컬·DB·서버 역할

| 위치 | 현재 역할 | 고도화 시 유지할 원칙 |
|---|---|---|
| 브라우저·기기 로컬 | 화면 상태·localStorage 저장본·사용자별 미저장 초안. 일반 localStorage를 암호화 저장소라고 부를 수 없음 | 편의와 임시 복구용. 수정 차감·고객 합의·권한의 최종 기준으로 삼지 않음. 로그아웃·계정 전환 격리 유지 |
| 네이티브 보안 저장 | 제한된 오프라인 스냅샷. 현재 최대 일감 30개·일감별 미완료 할 일 5개, 읽기 전용 경로 | 마지막 동기화 시각 표시. 앱의 모든 캐시가 암호화됐다고 표현하지 않음. 오프라인 수락·차감은 보류 |
| Supabase DB | 사용자별 workspace_documents가 현재 작업공간 기준. 저장 RPC가 문서 버전·재시도 키 검사. 고객 요청·기기·푸시 관련 데이터 | 새 요청·회차·수락·합의·발송 이력의 서버 원장을 설계. 기기가 꺼져도 데이터 유지. 고객·소유자 접근 분리 |
| Sites Worker·Supabase 서버 함수 | 화면 배포·일부 API, 계정 삭제 등 서버 처리와 푸시 발송·예약 호출 | 비밀키, 권한 판정, 예약 작업, 수락+차감 트랜잭션, 알림 발송. 모든 브라우저 요청이 Worker를 통과하는 구조는 아님 |

웹·앱은 같은 계정의 서버 데이터를 공유한다. 로컬 전용으로 만들면 고객 접수·다른 기기 동기화·기기 종료 중 예약 알림의 목적을 충족하지 못한다. 로컬 백업 파일과 운영 DB 복구 체계는 서로 다르다.

### 데이터 정합성·보안 설계

1. 요청 수락 시 소유자 권한, 일감·요청 버전, 현재 상태, 잔여 회차를 서버에서 검사한다.
2. 요청 수락·회차 반영·통지 예약을 한 DB 트랜잭션으로 기록한다. 재시도 키에 유일성 제약을 둔다.
3. 현재 전체 작업공간 JSON 저장이 새 서버 요청 상태를 덮어쓰지 않도록 별도 원장과 버전 충돌 처리를 먼저 설계한다. 문서 저장 방식과 무계획하게 이중 기록하지 않는다.
4. 발송 대기함(outbox)은 통지 예약과 실제 발송 결과를 나눠 관리한다. 전송 성공 여부가 불명확하면 공급사 결과를 확인하고 재시도한다. 외부 이메일의 절대적 1회 배달을 보장한다고 표현하지 않는다.
5. 고객 링크는 권한이다. 추측 방지·재발급·폐기·속도 제한을 유지하고, 새 승인 기능에는 필요한 만료·확인 절차를 설계한다. 링크 클릭 기록을 법적 본인 서명과 동일시하지 않는다.
6. 로그·분석에는 고객 본문·개인정보·공개 링크 토큰을 넣지 않는다. AI로 본문을 보내는 기능은 공급사·보관·동의 범위를 먼저 정한다.
7. 카카오 개인 대화·크몽 메시지·이메일함을 무단 수집하지 않는다. 초기에는 고객 링크와 사용자가 선택해 입력한 내용만 처리한다.

## 8. 서버·DB 운영 계획

**현행 Sites + Supabase를 유지하면서 복구·정지 위험을 먼저 관리한다 (추천).** 호스팅을 Cloudflare로 옮기는 것만으로 Supabase Free 유휴 정지 문제가 없어지지는 않는다. DB·Auth까지 바꾸는 일은 데이터·권한·로그인·RPC·푸시를 재검증하는 별도 프로젝트다.

- 2026-10-25 00:10:52 KST 읽기 전용 GET /api/health: HTTP 200, ready=true, DB 계약 202608250011 일치. 단일 응답 3,273ms이며 가동률·장시간 안정성·성능 백분위가 아니다.
- 같은 응답의 policyPublication.finalized=false. 정책·실제 탈퇴/복원 증거·실기기 등 기존 운영 게이트는 여전히 별도다. 신규 광고 유입을 즉시 사용 가능한 앱 출시라고 안내하지 않는다.
- [Supabase 요금](https://supabase.com/pricing): Free 유휴 정지 위험, Pro 월 $25부터. 조직의 다른 프로젝트·사용량·세금까지 포함한 실제 청구액은 결제 전에 확인한다. 이번 작업에서 유료 전환하지 않는다.
- [Supabase 백업 문서](https://supabase.com/docs/guides/platform/backups): Pro 일일 백업과 보관 조건, 별도 외부 백업·복원 훈련을 구분한다. DB 백업만으로 Storage 파일이 복원되지는 않는다. Auth·설정·비밀키 재구성도 복구 범위에 포함한다.
- 베타 운영 목표안: 최대 데이터 손실 허용 24시간(RPO), 복구 목표 4시간(RTO). 실제 복원 훈련을 통과하기 전 달성된 SLA라고 하지 않는다.
- 모니터링 제안: 5분 주기, 연속 3회 실패 시 알림. 예약 업무 실패·통지 대기 시간도 별도 관찰. 현재 새 모니터를 설치한 것은 아니다.
- 암호화된 별도 위치의 백업과 월 1회 별도 recovery 환경 복원 검증을 계획한다. 운영 DB에 실험 복원하지 않는다.
- GitHub는 코드·기획서 이력용이다. 고객 DB와 파일 백업을 대신하지 않는다. 비밀키·고객 데이터·서명 이미지는 커밋하지 않는다.

## 9. 구현할 때의 작은 작업 단위

체크박스는 미래의 인수 조건이며, 이번 조사로 완료 처리하지 않는다. UI 검증은 PRD 스킬의 ‘Verify in browser using dev-browser skill’ 기준을 따른다. 현재 dev-browser 스킬이 없으므로 실제 실행 시 사용 가능한 승인된 브라우저 도구로 동등 검증하고 도구·환경을 기록한다.

### US-001 · 미검토 요청 저장

작업자로서 접수된 요청을 읽기 전에 수정 한도가 줄지 않기를 원한다.

- [ ] 신규 정책 일감은 접수 상태와 진행 상태를 분리한다.
- [ ] 단순 조회·접수·중복 전송은 차감하지 않는 회귀 테스트를 추가한다.
- [ ] 기존 일감 정책·과거 차감 내역은 변경하지 않는다.
- [ ] typecheck·lint·관련 테스트 통과.

### US-002 · 수락과 1회 차감

작업자로서 내용을 확인한 후 한 번의 확정으로 수정 진행과 회차 반영을 끝내고 싶다.

- [ ] 권한·잔여·상태 검사와 수락·차감·통지 예약이 원자적으로 처리된다.
- [ ] 동시 수락·더블클릭·응답 유실 재시도에서 한 번만 차감된다.
- [ ] 잔여 0, 타인 요청, 폐기 일감은 거부한다.
- [ ] typecheck·lint·관련 테스트 통과.

### US-003 · 확인·수락 화면

작업자로서 요청 내용, 패키지 조건, 현재 잔여를 한 화면에서 보고 결정하고 싶다.

- [ ] ‘수정 진행 · 1회 사용’, ‘질문/보완’, ‘추가 협의’가 구분된다.
- [ ] 오류 보완·문의는 0회 사용으로 처리된다.
- [ ] 고객 화면에는 접수와 진행 확정이 서로 다르게 보인다.
- [ ] 브라우저에서 360px·데스크톱, 긴 요청·잔여 0·동기화 실패·이중 클릭을 검증한다.
- [ ] typecheck·lint·관련 테스트 통과.

### US-004 · 동일 회차 보충과 취소

작업자로서 한 번 확정한 수정 묶음의 보충 의견이나 실수 취소 때문에 회차가 잘못 집계되지 않기를 원한다.

- [ ] 보충 의견의 소속 회차와 변경 이력이 남는다.
- [ ] 수락 취소는 보상 이벤트로 기록하며 과거 원문·차감 이력을 삭제하지 않는다.
- [ ] 상태 변경 후 고객에게 표시되는 잔여와 서버 원장이 일치한다.
- [ ] typecheck·lint·관련 테스트 통과, 관련 UI 브라우저 검증.

### US-005 · 추가 조건 합의

작업자로서 포함 범위를 넘는 수정은 고객과 조건을 정한 다음 진행하고 싶다.

- [ ] 제안 범위·금액·예정일·제안 버전을 함께 표시한다.
- [ ] 미승인·거절·구버전 승인은 기존 금액·납기를 바꾸지 않는다.
- [ ] 승인된 변경을 원자적으로 적용하고 상태를 재조회한다.
- [ ] 링크 접근자를 법적 본인 인증 완료로 표시하지 않는다.
- [ ] typecheck·lint·관련 테스트 통과, 고객·작업자 UI 브라우저 검증.

### US-006 · 안내 발송과 실패 처리

작업자로서 진행 안내가 누락되거나 반복 발송되지 않기를 원한다.

- [ ] 고객 수신 동의·채널·재시도·전송 결과가 기록된다.
- [ ] 실패 시 작업자에게 보이고 수동 처리 경로가 있다.
- [ ] 원문·비밀 링크·타 고객 정보가 로그나 다른 수신자에게 노출되지 않는다.
- [ ] 자동 발송은 별도 발송 공급사·정책 준비 후 활성화한다. 초기에는 안내 문구 확인·복사만 제공할 수 있다.
- [ ] typecheck·lint·관련 테스트 통과, 실패 UI 브라우저 검증.

## 10. 기능 요구사항

- FR-01. 패키지 조건은 일감 생성 시 스냅샷으로 저장하고 소통 규칙도 동일하게 버전 관리한다.
- FR-02. 고객 접수와 작업자 진행 수락을 분리한다. 단순 읽기·접수 확인은 차감하지 않는다.
- FR-03. 작업자 수락과 차감·통지 예약은 서버에서 함께 확정한다.
- FR-04. 문의·오류 보완·보류·철회는 차감하지 않는다.
- FR-05. 추가 작업은 변경 조건의 명시적 합의 전 실행 상태로 전환하지 않는다.
- FR-06. 같은 수정 묶음의 보충 내용은 새 회차와 구분하고 자동으로 새 회차를 차감하지 않는다.
- FR-07. 처리 취소·정정은 이력으로 남기며 고객 잔여와 서버 원장의 불일치를 차단한다.
- FR-08. AI의 분류·답변은 초안이다. 가격·차감·납기·고객 발송의 최종 권한은 정한 정책과 사람에게 있다.
- FR-09. 외부 채널 자동 수집은 공식 권한·약관·보안 검증을 별도로 통과해야 한다.
- FR-10. 오프라인에서는 최종 확정 상태를 읽되 수락·차감을 서버 확인 없이 완료로 표시하지 않는다.

## 11. 지금 하지 않을 것

- 세금 신고·법률 판단·결제 대행을 현재 기능으로 포장하기.
- 공급업체의 생성 도구를 광고 운영 대행·고객 모집 완료로 계산하기.
- 완전 자동 CS, 고객 메시지의 무단 수집, 조건 없는 수정 자동 차감.
- 기획을 근거로 기존 고객 데이터·요금·정책을 바로 바꾸기.

## 12. Git·운영 반영 순서와 다음 결정

기획 문서는 별도 브랜치에서 검토·커밋·push하고 PR로 남긴다. 이 문서 PR은 앱 배포를 요구하지 않는다. 구현 시에는 작은 변경별 테스트→리뷰→CI→승인된 병합→배포 후 점검 순서로 진행한다. DB는 기존 앱과 호환되는 마이그레이션·되돌림 방안을 먼저 준비한다.

남은 결정은 ① 기존 일감과 새 회차 정책의 적용 경계 ② 초기 발송 방식과 공급사 ③ 실제 파일럿 타깃·비교 도구 ④ 유료 DB 운영비 승인이다. 이번 계획은 고객 사례 검증과 구현 범위 합의용이며, 법적 조건·구매·외부 발송 승인으로 사용하지 않는다.

AI 지원금의 공급사 역할·금액·한계는 [별도 검토표](../docs/research/2026-10-25-AI지원금-업체역할.md)에 정리했다. 도구 구독과 실제 고객 유치 대행을 분리한다.
