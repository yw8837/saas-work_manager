# 새 수정 요청 알림 — 방식 비교와 제안 (설계만, 구현 전)

작성 2026-11-01 · 기준 브랜치 `claude/revision-count-clarity` · 계기: 외주 경험자 대화(납품 뒤 급한 수정이 오면 바로 알아야 함, 스테이션 `과제/2-MVP/서비스반영후보-외주경험자대화-2026-11-01.md` 1번 표 3번).

## 방식 비교

| 방식 | 작업자가 받는 경험 | 새로 필요한 것 | 위험·한계 |
|---|---|---|---|
| A. 웹 푸시(기존 대기열 재사용) | 브라우저·홈 화면 앱으로 알림. 누르면 해당 일감으로 | 기기 플랫폼에 `web` 허용(migration), 웹 구독 등록 화면(설정), 발송 함수에 웹 푸시 형식 추가, FCM 웹 설정 또는 VAPID 키(비밀값은 서버에만) | iPhone은 홈 화면에 추가한 앱에서만 웹 푸시가 된다. 브라우저 권한을 거부하면 못 받는다 |
| B. 메일 알림 | 메일함으로 "새 요청 1건" | 메일 발송 서비스 계정, 보내는 도메인 인증(SPF·DKIM), 발송 함수, 작업자별 수신 설정 | 메일 서비스 비용·한도 확인 필요. 스팸함으로 갈 수 있다. 인증 메일과 분리해 새로 설계해야 한다(SMTP 문서 방침) |
| C. 카카오 알림톡 | 카톡으로 알림 | 비즈니스 채널·발신 프로필 심사, 템플릿 심사, 건당 비용 | 심사·비용이 들고 지금 단계에서 과하다 |

## 제안

1. **A(웹 푸시)를 먼저 한다.** 대기열·재시도·발송 함수·서비스 워커가 이미 있어서 새로 만드는 범위가 가장 작다. Android 앱 알림의 원칙("고객 이름과 요청 내용은 잠금화면에 표시하지 않아요", `native-push-settings.tsx` 41행)과 앱 안 알림의 비공개 설정(`settings.privateNotificationDetails`, `today-dashboard.tsx` 200행)을 그대로 따른다.
2. 알림이 꺼져 있거나 못 받는 사람을 위해, 앱을 열면 확인 대기 건수를 맨 위에 보여 주는 지금 방식은 유지한다.
3. B(메일)는 A로 놓치는 사람이 실제로 생기면 그때 검토한다.

## 구현할 때 지킬 것 (보안·DB)

- 웹 구독 정보(엔드포인트·키)는 서버의 기기 표에만 저장하고, 주인만 등록·해제할 수 있게 한다(지금 Android 기기 등록과 같은 권한 규칙). 익명에게는 열지 않는다.
- VAPID 비밀키·FCM 서버 키는 Edge Function 비밀값에만 둔다. Git·브라우저 환경변수·로그에 넣지 않는다.
- 알림 본문에는 기본으로 고객 이름·요청 원문을 넣지 않는다("새 수정 요청이 들어왔어요"). 작업자가 켠 경우에만 일감 이름을 보인다.
- 끝난(410) 구독은 발송 함수가 자동으로 끈다. 재시도는 지금 대기열 규칙(최대 5회)을 그대로 쓴다.
- 배포 순서는 새 앱과 옛 DB, 옛 앱과 새 DB가 각각 맞물리는지 확인하고 정한다(기기 등록 허용값을 넓히는 migration은 보통 먼저 적용해도 옛 앱에 해가 없다).

## 사용자가 정할 것

- A로 갈지(추천), 외부 설정(Firebase 콘솔의 웹 푸시 설정 또는 VAPID 키 발급)을 누가 할지. 콘솔 로그인·키 발급은 사용자 계정 작업이라 사용자 승인과 직접 확인이 필요하다.
