## 2. 목표 흐름과 남은 차이

목표(사용자 설명): **요청 접수 → 제작자 확인·수락 또는 추가 작업 협의 → 수정/결과 전달 → 고객 확인 → 차감**

| 목표 단계 | 지금 | 남은 차이 |
|---|---|---|
| 요청 접수 | 확인 대기 | 없음 |
| 제작자 확인·수락 | 별도 '수락' 단계는 없고, 반려/추가 작업/수정 완료 중 하나를 고른다 | 수락만 먼저 표시하는 단계는 없다(필요하면 D9) |
| 추가 작업 협의 | '추가 작업으로' 분류 + 추가요청 기록 | 고객 동의는 앱 밖(평소 대화창) |
| 수정/결과 전달 | 작업자가 '수정 완료'를 누르면 1회 | 결과물 전달 기록은 없다 |
| 고객 확인 | 없음 | 고객 확인 뒤 차감은 하지 않는다(D2) |

## 4. 고객이 링크를 열 이유와 부담

- **열 이유:** 로그인 없이 남은 수정 횟수·확인 대기 건수·마감·진행 단계, 아직 보내지 않은 자료를 본다. 요청이 기록으로 남고, 질문은 횟수에 들어가지 않는다(작업자가 반려).
- **부담:** ① 대화창에서 한 번 더 이동한다. ② 답은 여전히 평소 대화창으로 온다. ③ 웹 사용자는 새 요청 알림을 못 받는다(설계만 함). ④ 크몽 한 채널 거래에서는 크몽 자체 기능과 겹친다. 외부 링크 허용은 약관 확인 전. ⑤ 제출 전 안내 상자가 입력란을 아래로 민다(체험 화면 실측 375×760에서 172px, 이번 문구 변경 뒤 다시 잼).
- **설계 의도(사용자, 2026-11-02):** 고객 링크는 대화창을 대신하는 곳이 아니라 **수정 요청만 받는 정해진 통로**다. 모두싸인처럼 계약서 서명은 받은 링크에서 하는 게 당연하듯, 작업자가 거래 시작 때 "수정 요청은 이 링크로"를 규칙으로 정해 두면 고객이 링크를 쓸 이유가 생긴다는 가설이다. 이 비유는 검증이 아니며, 바로 아래 반증점으로 확인한다.
- **응답자 반론(가장 중요한 반증점):** 2026-11-01 외주 경험자 탐색 대화(1명, 사용 검증 아님)에서 응답자가 "고객이 별도 서비스 링크를 실제로 누를까"라고 물었다. 고객이 링크 대신 평소 대화창으로 요청을 보내면 작업자가 그 내용을 일감체크에 다시 옮겨 적어야 해서, 일이 줄기는커녕 늘 수 있다. 그래서 첫 실측은 **고객이 링크에 직접 남긴 주문**과 **대화창으로 받아 작업자가 기록한 주문**을 함께 본다. 어느 쪽이든 같은 요청을 두 번 입력하게 되면 '잡무 감소' 주장을 거두거나 고객 경로를 바꾼다(HANDOFF '다음 작업' 3번과 같은 기준).
- **확인 못 한 것:** 실제 고객이 링크를 여는 비율(열람 기록 없음, 운영 DB 권한 없음).

## 5. 보안·DB 처리

### 이번 변경의 DB 영향

- migration 1개(`20261101140000`): 원장 `usage` 허용값에 `pending` 추가, 공개 제출 함수 교체(확인 대기로만 기록), 고객 조회 함수를 지우고 다시 만듦(열 2개 추가). 권한 부여문은 다시 적었다.
- 시험: 모든 migration을 적용한 PGlite에서 `supabase/tests/revision_pending_submit.sql` — 제출이 확인 대기인지, 멱등 재시도, 대기 건수·받을 자료(빈 이름·받은 항목 제외), 작업자 저장 뒤 1회 반영, 허용 안 된 `usage` 거부, 익명 권한 그대로. 이 migration을 빼면 `submit_not_pending: used 1 0`으로 실패하는 것을 확인했다.
- 적용 순서: **새 앱 배포 → 곧바로 migration.** 새 앱은 migration 전 DB와도 맞는다(옛 영수증 `used`/`extra_scope` 처리, 조회 함수에 새 열이 없으면 표시 생략). 반대로 이전 앱은 `pending` 영수증을 '추가 작업 검토'로 잘못 안내하므로 migration을 먼저 하면 안 된다(Codex 4차 P2).
- **순서로 못 막는 것(Codex 5차 P2):** 새 앱 배포 전에 열어 둔 고객 탭은 옛 화면 코드 그대로다. migration 뒤 그 탭에서 제출하면 "포함된 수정 횟수를 넘어 추가 작업 검토 요청으로 기록됐어요"라고 잘못 안내한다(옛 코드는 `used`가 아닌 영수증을 모두 추가 작업으로 본다). 두 단계 사이를 짧게 해도 해결되지 않는다. 데이터는 확인 대기로 맞게 남고, 그 탭을 새로 고치면 바로잡힌다. 배포 시점에 실제 고객이 링크를 쓰고 있다면 작업자가 그 요청을 확인할 때 고객에게 한 번 바로잡아 알려야 한다. 이를 코드로 막으려면 제출 함수가 옛 화면용 값과 새 화면용 값을 따로 돌려주는 호환 열이 필요하다(지금은 안 함).
- 배포와 migration 사이에 들어온 고객 요청은 옛 규칙(접수 즉시 1회)으로 기록되고 그대로 남는다.

### 설계 원칙에서 달라진 점 (밝혀 둠)

앞선 초안의 원칙 1("차감 확정은 서버 함수 안에서")과 달리, **'수정 완료'·'추가 작업으로'·'반려'는 작업자 화면이 자기 문서를 저장하는 기존 경로(`save_workspace_document`)로 처리했다.** 이유와 안전장치:

- 수정 횟수는 작업자 본인의 기록이다. 고객은 공개 제출 함수로 확인 대기 요청을 **추가**만 할 수 있고, 횟수·상태를 바꿀 수 없다.
- 일반 저장은 문서 버전으로 낙관적 잠금을 한다. 고객 제출이 먼저 들어와 버전이 올라가면 작업자의 오래된 저장은 서버에서 거부된다(덮어쓰지 않음). 작업공간은 서버 문서와 3갈래 합치기를 한다. 배열은 기록 id별로, 기록 안은 필드별로 합쳐서, 고객이 새로 남긴 요청(새 id)과 작업자의 '수정 완료'(기존 기록의 필드 변경)를 둘 다 살린다. 같은 필드를 양쪽이 바꾼 진짜 충돌은 자동 저장하지 않는다(`workspace-provider.tsx`의 `mergeWorkspaceValue`). 이 경우는 `workspace-provider.test.ts`의 합치기 시험으로 확인했다.
- 되돌리기·추가요청 확정 같은 기존 작업자 동작도 같은 경로를 쓴다.
- **여러 기기 보호(Codex 4·5차 P1·P2 반영):** ① 저장 충돌 때 '고객 요청이 새로 붙은 것뿐'인지는 기존 기록이 하나도 안 바뀐 경우로만 판정한다(`isPublicRevisionAppendOnly`). 다른 기기의 '수정 완료'처럼 기존 기록이 바뀌었으면 3갈래 필드 합치기로 가서, 오래된 확인 대기로 덮어쓰지 않는다. ② 두 기기가 서로 다른 요청을 각각 완료해서 합친 결과가 포함 한도를 넘거나 회차 번호가 겹치면 충돌로 보고 자동 저장을 멈춘다(이 기기의 편집은 보존, 새로고침 뒤 다시). 원래부터 깨진 기록 때문에 막히지 않도록 공통 조상과 서버본 중 가장 나쁜 정도(초과 횟수·겹친 회차 수)와 비교해, 그보다 늘어난 경우만 고른다. 이 기기 화면은 기준에서 뺀다. 엔진은 한도를 넘는 완료나 겹친 회차를 만들지 않으므로 화면에만 있는 위반은 충돌을 멈출 때 다른 기기 기록이 붙어서 생긴 것이고, 그걸 인정하면 '이 기기 편집으로 재시도'나 새로고침 복구가 한도 초과본을 저장한다(Codex 7차 P2, 양쪽이 각각 '수정 완료로 기록'한 경우). ③ '추가만' 경로에서도 같은 검사를 한다. 다른 기기가 '수정 완료로 기록'한 수동 기록도 새 id라서 이 경로로 들어오기 때문이다(`resolveHostedSaveConflict`). ④ 큐에서 기다린 저장은 넣을 때 찍은 스냅샷이 아니라 실행 시점의 화면 상태를 보낸다. 앞선 저장이 합쳐 넣은 다른 기기 변경을 뒤 저장이 되돌리지 않게 하려는 것이다. ⑤ 문서 저장이 성공하면 링크 동기화보다 먼저 동기화 기준과 화면을 갱신하고, 충돌 재시도 저장은 성공한 뒤에만 버전 기준을 올린다(링크 동기화나 재시도 저장이 실패해도 다음 저장이 옛 화면을 새 버전으로 보내지 않음). ⑥ 서버 응답을 기다리는 동안 생긴 기록을 붙인 최종본을 다시 검사한다. ⑦ '이 기기 편집으로 재시도'도 같은 항목 충돌은 이 기기 편집을 따르되, 한도 초과·회차 중복이 새로 생기면 저장하지 않고 한쪽 완료를 되돌리거나 서버본을 쓰라고 안내한다. 근거·시험: `workspace-provider.tsx`의 위 함수들과 `persistHostedState`·`resolveHostedDraft`, `workspace-provider.test.ts`(합치기·판정), `workspace-provider-session.test.tsx`(기대 버전이 다르면 거부하는 가짜 서버로 실제 저장 큐 재현: 충돌 재시도 성공·링크 동기화 실패·재시도 저장 실패 때 완료 유지, 대기 중 수동 완료 기록, 로컬 우선 복구, 양쪽 기기의 수동 완료 기록 뒤 로컬 우선 복구·새로고침 복구). 각 수정을 하나씩 되돌리면 해당 시험이 실패하는 것을 확인했다.
- 남은 위험: 작업자가 자기 문서를 직접 고치면 횟수를 바꿀 수 있다(본인 데이터라 보안 경계 밖). 고객 확인처럼 **고객이 상태를 바꾸는 단계**를 넣을 때는 원칙 1~3대로 서버 함수·상태 전이 검사·권한 분리를 해야 한다.

### 앞으로 상태를 더 늘릴 때 지킬 것

1. 고객이 상태를 바꾸는 단계(고객 확인 등)는 `security definer` 함수로 만들고, 문서 → 링크 잠금 순서를 쓴다.
2. 허용된 상태 전이만 DB에서 통과시키고, 재시도는 멱등 키로 1번만 반영한다.
3. 작업자 동작은 주인(`auth.uid()` = owner)만, 고객 동작은 링크 토큰 해시로만. 새 함수마다 PGlite 권한 시험을 더한다.
4. 기록은 지우지 않고 쌓는다. 원장에 새 필드를 두면 원문 수정 금지 트리거를 더한다(지금 원장에는 없다).
5. 데이터 이행이 필요하면 한 트랜잭션으로, 백업·되돌림 SQL을 준비하고, 앞뒤 숫자를 대조한다. 배포 순서는 새 앱과 옛 DB, 옛 앱과 새 DB가 각각 맞물리는지 보고 정한다(이번 건은 앱 먼저).
6. 새로 모으는 정보는 최소로 한다(열람 기록을 넣으면 시각만, IP·기기 정보 저장 안 함, 처리방침 먼저 수정).
7. 서버가 관리할 필드가 생기면 일반 저장(`save_workspace_document`, `202608200007_plan_entitlements.sql` 303~306행)이 그 값을 덮어쓰지 못하게 막는다.
8. 링크 토큰 원문을 문서 JSON에서 빼는 것도 함께 검토한다(해시 비교로 바꾸고 기존 원문 제거, 과거 백업은 보유·폐기 정책을 따름, `scripts/supabase-backup.mjs` 23행).
