# 모바일 베타 운영 기준

## 배포와 외부 공개를 구분한다

웹/API 배포와 내부 Android 설치 파일 제작은 개발 완료 검증이다. 외부 이용자에게 APK를 배포하거나 모집을 시작하려면 아래 공개 조건을 모두 충족해야 한다. 자동 검사 성공을 실기기 성공·정책 승인으로 대체하지 않는다.

| 조건 | 통과 증거 | 현재 처리 |
| --- | --- | --- |
| 웹·앱 동일 계정 | 실제 Google 로그인 후 같은 일감 ID·내용을 양쪽에서 확인 | 실기기 확인 필요 |
| 양방향 저장 | 웹 수정→앱 복귀, 앱 수정→웹 새로고침. 충돌 시 초안 보존 | 자동 회귀 통과, 실기기 확인 필요 |
| 수정 요청·알림 | 고객 링크 제출 1회→횟수 1회 반영→잠금화면 알림→해당 일감 이동 | 서버 연결과 실기기 표시를 각각 기록 |
| 계정 분리 | A 로그아웃→B 로그인→A 데이터/푸시 미표시 | 세션 전환 회귀 통과, 실기기 확인 필요 |
| iPhone | 서명된 빌드 설치·APNs·Google 복귀 | Mac/Xcode·Apple Developer·APNs 준비 필요 |
| 개인정보 안내 | 아래 추가 항목의 운영·법률 검토, 게시 버전·동의 일치 | 승인 전 초안, finalized=false 유지 |
| 삭제·복구 | 전용 Google 테스트 계정의 실제 탈퇴와 별도 복구 환경 검증 | 기존 G12~G15 운영 증거 필요 |

## 개인정보 안내에 추가할 사실 — 게시 승인 전 초안

이 내용은 코드와 서버 설정에 근거한 사실 정리다. 법률 검토 완료나 게시 확정을 의미하지 않는다. 특히 국외 처리 국가·방법·시점·보유기간·거부 절차는 제공자 최신 조건과 운영 주체의 확인이 필요하다.

| 목적 | 처리 항목 | 실제 보관·삭제 동작 |
| --- | --- | --- |
| 휴대폰 알림 | 계정 ID, 설치 ID, OS 종류, FCM 등록 토큰, 활성 상태·갱신 시각 | 기기 등록 해제·로그아웃 성공 시 삭제, 계정 삭제 시 연쇄 삭제. 무효 토큰은 비활성화하며 별도 30일 자동 삭제는 현재 없음 |
| 알림 재시도 | 수정 요청 ID, 기기 ID, 발송 횟수·결과·시각·lease | 관련 요청/기기/계정 삭제에 연동. 독립적인 기간 만료 정리 정책은 아직 없음 |
| 서버 예약 호출 위조 방지 | 무작위 호출 nonce, 만료 시각 | 5분 만료 후 1분 여유를 두고 다음 호출에서 정리. 고객명·토큰·본문 없음 |
| 모바일 재로그인·오프라인 조회 | 세션, PKCE verifier, 서버 저장을 확인한 진행 중 일감 최대 30건 | Android Keystore/iOS Keychain 기반 기기 보안 저장소. 오프라인은 읽기 전용이며 계정 불일치 시 접근 차단 |
| 웹 초안 복구 | 계정별 작업 상태·저장 전 초안 | 브라우저 저장소도 사용한다. ‘Hosted 모드에는 기기 저장이 없다’고 안내하지 않는다. 웹 로컬 저장소를 OS 암호화 저장소라고 표현하지 않는다 |

추가 처리자: Google Firebase Cloud Messaging. 목적은 앱 알림의 전달이며 Firebase Auth/Firestore로 계정·일감 DB를 이전하는 것이 아니다. Firebase Analytics는 활성화하지 않았다. FCM 토큰과 일반 알림 문구, 요청 ID·일감 ID를 사용하며 고객명·수정 요청 본문은 푸시 payload에 넣지 않는다. iOS APNs는 준비 예정이며 실제 연결·검증과 구분한다.

권리 안내 초안: 앱 설정에서 알림 등록을 해제하고 OS 알림 권한도 철회할 수 있다. OS 권한 철회와 서버의 기기 등록 삭제는 같은 작업이 아니므로 서버 해제 결과를 별도로 확인한다. Google의 자체 토큰 보관 기준과 우리 DB의 삭제 기준도 구분한다.

서비스 범위 안내 초안: 고객 링크로 접수된 새 수정 요청을 휴대폰 알림으로 전달한다. 수동 수정 기록·마감·일일 브리핑은 현재 예약 푸시 대상이 아니다. FCM 접수 성공은 휴대폰 표시 보장이 아니며, 네트워크·OS·권한 상태에 따라 지연될 수 있다.

참고: [Firebase 개인정보·보안](https://firebase.google.com/support/privacy), [FCM 토큰 관리](https://firebase.google.com/docs/cloud-messaging/manage-tokens).

## 운영자가 확인할 순서

1. `https://ilgam.studioyeolmae.com/api/health`의 ready와 런타임 계약을 확인한다. HTTP 200만으로 로그인·저장 성공을 판단하지 않는다.
2. Supabase 프로젝트 `evhkpgxacpweelnmjmqh`의 cron `ilgam-native-revision-push`가 1개인지 확인한다. 활성 상태·최근 실행과 Edge 응답을 함께 본다.
3. 등록 기기와 due attempts가 없다면 cron 성공은 빈 큐 정상 처리다. 알림 전달 실적으로 세지 않는다.
4. 실패 시 attempts 상태·횟수·lease를 본다. 최대 5회 재시도와 현재 토큰 일치 조건을 유지한다. 푸시 실패를 해결하려고 수정 횟수를 다시 증가시키지 않는다.
5. 장애 시 해당 cron만 비활성화한다. DB·고객 요청·일감은 삭제하지 않는다. 키가 노출된 경우 서버/Vault를 함께 교체하고 서명 검증을 다시 수행한다.

## 서명 호출의 보안 경계

pg_net 관리 객체는 Supabase 관리자 소유이며 프로젝트 postgres의 REVOKE가 효과를 내지 않는다. 따라서 요청 큐에 장기 비밀키를 넣지 않는다. 프로젝트 주소·메서드·경로·고정 본문 hash·시각·nonce를 HMAC으로 서명하고 Edge가 최대 90초의 서명과 일회성 nonce를 확인한다.

이는 큐 자체의 ACL을 고친 것이 아니다. DB에 직접 로그인할 수 있는 역할은 여전히 큐를 읽거나 변경할 수 있어, 유효한 호출과 경쟁하거나 전송을 방해할 수 있다. 기본 익명 Data API 사용자가 바로 큐를 읽을 수 있다는 뜻도 아니다. DB 로그인 권한은 운영자에게만 제한해야 한다.

근거: [Supabase pg_net 권한 제한](https://supabase.com/docs/guides/troubleshooting/revoking-access-to-pg_net-objects-has-no-effect-0bbc16).

## 실제 휴대폰 검증표

- Android APK 설치 → Google 로그인 → 앱 복귀 → Today 진입.
- 전용 테스트 일감 1건만 생성 → 웹/앱 각각 변경 → 상대 화면에 저장 내용 확인.
- 고객 링크에서 수정 요청 → 횟수 정확히 1회 → 앱 전면·백그라운드·잠금화면 각각 확인.
- 같은 알림 재탭 → 수정 횟수 추가 차감 없음.
- 알림 해제 → 이후 요청에 해당 기기 발송 없음.
- 비행기 모드 → 서버 확인 스냅샷만 읽기 → 편집 차단 → 재연결 후 최신 상태 확인.
- 계정 전환 → 이전 계정 데이터·오프라인 스냅샷·알림 대상 접근 차단.
- 테스트 데이터 삭제는 정확한 대상에 대한 승인을 받은 뒤 수행.

결과는 기종·OS·APK SHA-256·계정 종류·확인 시각과 함께 기록한다. 현재 연결된 실기기 없이 체크 표시를 채우지 않는다.
