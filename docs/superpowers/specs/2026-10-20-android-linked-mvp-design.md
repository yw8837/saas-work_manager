# 일감체크 Android·iPhone 연동 MVP 설계

작성일: 2026-10-20  
산출물: Android 설치 APK + iPhone 앱 및 TestFlight 테스트 배포 준비  
상태: **서면 설계 검토용. 앱 구현·설치·실기기 검증 완료를 뜻하지 않는다.**

검토 이력: Android 설계는 사용자가 승인했다. 이후 “사용자가 Android라는 보장이 없다”며 iPhone 동시 개발을 요청했다. 아래 iOS 추가 범위와 배포 환경을 구현 계획에 함께 반영한다. 파일명은 이미 공유한 링크를 보존하기 위해 유지한다.

## 1. 만들 것

웹에서 쓰던 Google 계정으로 앱에 로그인하면 같은 패키지와 일감이 보인다. 앱에서도 일감을 등록하고 할 일을 처리하며, 고객의 수정 요청을 확인한다. 웹과 앱을 동시에 열어도 한쪽의 변경이 다른 쪽에서 사라지지 않아야 한다.

고객 링크로 접수된 수정 요청은 서버가 한 번만 반영한다. 알림 수신이나 알림 누르기는 수정 횟수를 다시 차감하지 않는다. 앱이 백그라운드에 있거나 일반적으로 종료된 상태에서도 알림을 받을 수 있게 한다.

사용자는 Android 설치 APK로 먼저 검증하고, iPhone도 같이 개발하도록 요청했다. iPhone 베타 배포는 TestFlight를 권장한다. 이번에는 Google Play·App Store 정식 공개 출시나 유료 서비스 전환을 하지 않는다. 외부 테스터 초대·공개 링크 배포는 승인 전 수행하지 않는다.

## 2. 선택한 구조

**기존 React 화면과 업무 로직을 공유하는 Capacitor Android·iOS 앱을 사용한다.** 계정과 데이터는 기존 Supabase를 그대로 사용한다. 새 사용자 DB나 별도의 앱용 일감 사본을 만들지 않는다.

| 방식 | 장점 | 부담과 판단 |
| --- | --- | --- |
| 기존 웹과 코드를 공유하는 Capacitor 앱 | 웹과 앱의 업무 규칙을 같이 유지하며 APK를 만들 수 있다 | 네이티브 로그인 복귀·푸시·앱 재개 처리는 추가해야 한다. 이번 선택 |
| Kotlin 또는 별도 모바일 UI | Android에 특화된 화면을 자유롭게 만들 수 있다 | 같은 기능을 웹과 앱에 각각 구현·검수해야 한다. 이번 범위에서 제외 |
| 웹 바로가기/PWA만 제공 | 기존 배포를 곧바로 이용할 수 있다 | 사용자가 선택한 설치 APK 및 네이티브 검증과 다르다. 대체 완료품으로 제시하지 않는다 |

Firebase를 사용하면 **FCM 알림 전송 용도**다. Supabase 인증·DB를 Firebase로 이전하지 않는다.

기존 제품 소스는 로컬 `a409b9f`, 확인한 원격 main은 `cafa8b8`이다. 실제 구현은 최신 main을 기준으로 한다. 현재 미커밋 문서와 사용자 자료를 덮어쓰거나 임의로 정리하지 않는다.

## 3. 화면과 사용 흐름

- 기존의 흰 바탕·먹색 글자·얇은 구분선 및 검정 일감체크 아이콘을 유지한다.
- 여러 일감을 전제로 제목·고객·마감·상태를 구분한다. 같은 고객의 서로 다른 일감도 식별돼야 한다.
- 오늘 할 일, 일감 목록, 수정 요청에서 상세로 이동하고 돌아올 때 필터·검색 조건을 유지한다.
- 앱에서도 패키지 선택 → 새 일감 등록 → 할 일 처리 → 수정 요청 확인을 수행한다. 단순 알림 뷰어로 제한하지 않는다.
- 저장 중 중복 탭을 막고, 실패 시 입력을 보존한다. 저장 실패를 성공으로 표시하지 않는다.
- 오프라인에서 마지막으로 확인한 데이터를 볼 수 있지만, 서버에 반영되지 않은 초안을 저장 완료로 표시하지 않는다. 재접속 시 최신본과 충돌하면 사용자가 확인하도록 한다.
- 알림을 누르면 로그인 상태와 해당 계정의 접근 권한을 확인한 뒤 대상 일감으로 이동한다. 일감이 삭제됐거나 접근할 수 없으면 안전한 안내와 목록으로 보낸다.

기존 모바일 시안의 예시 고객·가상 주문을 운영 데이터나 실제 고객 사례로 옮기지 않는다.

## 4. Google 로그인과 세션

1. Android에서는 외부 브라우저/Custom Tab, iOS에서는 시스템 브라우저 인증 흐름으로 Google 로그인을 연다. WebView 안에서 Google 자격 증명을 입력하게 하지 않는다.
2. Supabase OAuth는 PKCE를 사용한다. 앱은 허용된 앱 복귀 URI만 처리하고, 인증 코드는 앱에 보관한 verifier와 교환한다.
3. 앱 복귀 URI는 `com.yeolmaestudio.ilgamcheck://auth/callback`으로 한정한다. 앱에서 시작한 미완료 로그인과 만료 시간을 확인한다. 임의 호스트·경로·토큰 fragment·반복 callback은 거절한다.
4. 로그인 버튼을 여러 번 눌러 verifier가 덮어써지지 않도록 한 번에 한 로그인만 진행한다. 취소·만료 시 다시 시도할 수 있다.
5. 세션과 verifier는 Android Keystore 기반 암호화 저장소, iOS Keychain에 보관한다. 토큰을 로그·분석 이벤트·알림·클립보드에 넣지 않는다. iOS 재설치 후 Keychain 잔존으로 이전 사용자에게 자동 연결되지 않도록 설치 식별자와 세션 수명을 구분한다.
6. 앱이 완전히 닫힌 상태에서 로그인 복귀 링크가 열려도 초기 URL을 처리한다. 화면이 살아 있는 상태의 URL 이벤트와 중복 처리하지 않는다.
7. 로그아웃·계정 전환 때 이전 계정의 화면과 로컬 초안·활성 알림 연결을 정리한다. 새 계정이 이전 계정의 일감을 잠깐이라도 표시하지 않도록 한다.

기존 웹 로그인 경로와 재인증 후 계정 삭제 기능을 유지한다. Supabase의 redirect 허용 목록을 넓은 wildcard로 바꾸지 않는다. 실제 Auth 설정 반영은 기존 값 확인과 변경 범위 보고 후 진행한다.

iOS 외부 테스트 심사 전 Apple 로그인 서비스 정책 4.8에 따라 대체 로그인 적용 여부를 검토한다. 기본 대응은 iOS에 Apple 로그인 선택지를 추가하는 것이다. 기존 사용자는 Google로 로그인하면 기존 계정을 그대로 사용한다. Apple의 비공개 이메일을 기존 Google 사용자와 이름만으로 자동 병합하지 않는다. Apple provider 설정은 계정·키 준비와 변경 범위 확인 후 수행한다.

## 5. 웹·앱 데이터 동기화

서버의 `workspace_documents`와 기존 버전 기반 저장 RPC를 기준으로 한다. 네이티브 앱도 기존 권한 검사·플랜 제한·저장 영수증 및 충돌 복구를 통과해야 한다.

- 최초 로그인, 앱 재개, 네트워크 복구 시 서버 최신본을 확인한다.
- Realtime은 빠른 갱신을 위한 수단이다. 알림이나 Realtime을 놓쳐도 재조회로 복구한다.
- 저장되지 않은 로컬 변경이 있으면 원격 갱신으로 덮어쓰지 않는다. 서버 버전과 로컬 기준 버전을 대조하고 기존 충돌 복구 흐름으로 연결한다.
- 앱과 웹의 동시 저장은 중복 키·버전 검사를 유지한다. 실패한 저장을 무조건 반복해 다른 기기의 변경을 지우지 않는다.
- 수정 요청 ID를 기준으로 접수와 횟수 반영을 한 번만 수행한다. 화면 새로고침·푸시 재전송·동일 링크 재시도는 별도 요청으로 세지 않는다.
- Android의 `localhost` 기준 상대 API 주소를 운영 서버 주소로 착각하지 않는다. 공개 설정·계정 삭제 등 서버 API는 허용된 HTTPS origin을 사용하는 공통 경계를 둔다.
- 인증이 필요한 네이티브 요청은 사용자 access token으로 인증한다. APK에는 service-role 키, FCM 서버 자격 증명, 서명키를 넣지 않는다.

웹 계정 삭제는 현재 정책을 유지한다. 실제 사용자 계정 삭제로 시험하지 않는다.

## 6. 수정 요청 푸시

푸시는 앱과 서버 두 부분으로 나눈다.

### 앱

- 사용자가 수정 요청 알림을 켤 때 Android 알림 권한을 요청한다. 거절해도 일감 관리·수정 요청 조회는 사용할 수 있다.
- iOS도 알림 권한을 별도로 요청하고 APNs capability·서명 환경을 확인한다. Android FCM 토큰과 iOS APNs 토큰을 같은 형식으로 취급하지 않는다. FCM을 공통 서버 전송 경로로 사용할 경우 iOS에는 Firebase Messaging 및 APNs 연결을 명시적으로 구현한다.
- 기기 토큰은 로그인한 계정과 설치 식별자에 연결한다. 갱신·다중 기기·로그아웃·계정 전환을 처리한다.
- 잠금 화면에는 “새 수정 요청이 도착했어요”처럼 최소 정보만 표시한다. 고객 이름·요청 원문을 기본 알림에 노출하지 않는다.
- 포그라운드에서는 같은 요청을 OS 알림과 앱 안내로 중복 표시하지 않는다.
- 알림 payload의 외부 URL을 그대로 열지 않는다. 허용된 내부 식별자로 서버 권한을 재확인한다.

### 서버

- `workspace_revision_requests`의 성공한 접수와 같은 트랜잭션에 발송 대기 기록을 남긴다. 푸시 실패 때문에 이미 접수된 수정 요청을 되돌리지 않는다.
- 기존 초기 스키마의 Web Push 테이블은 별도 정규화된 jobs/revision_requests를 참조한다. 이를 현재 workspace 문서 모델에 그대로 연결된 것으로 가정하지 않는다.
- 현재 workspace 모델용 기기 등록·발송 대기·재시도 기록을 명확하게 분리한다. RLS로 사용자가 다른 계정의 기기 토큰을 조회하거나 발송 대기를 임의 작성하지 못하게 한다.
- 서버 함수만 FCM 자격 증명을 사용한다. 요청 ID와 기기 ID로 중복을 억제하고, 제한된 재시도와 무효 토큰 정리를 수행한다.
- DB 발송 기록과 FCM 접수 성공은 실제 휴대폰 표시와 구분한다. 실기기 수신으로 최종 확인한다.
- 운영 적용 전 테스트 계정으로 마이그레이션·롤백·발송 실패 복구를 확인한다.

Android 설정에서 앱을 **강제 종료(force-stop)**하면 OS가 푸시를 막을 수 있다. 이를 우회하거나 도착을 보장하지 않는다. 일반 백그라운드·최근 앱 종료·강제 종료는 검증 결과에 따로 표시한다. 앱을 다시 열면 서버 재조회로 요청을 복구해야 한다.

FCM 프로젝트·공개 Android 설정·서버 자격 증명·발송 실행 환경이 준비되지 않으면 “푸시 완료”로 표시하지 않는다. 새 외부 프로젝트 생성·유료 전환·운영 마이그레이션은 필요한 단계에서 범위를 제시한다.

## 6-1. iPhone 전용 구현·배포 경계

- 기존 `ios/App` 프로젝트를 사용한다. iOS URL scheme, SceneDelegate의 cold/warm callback, Keychain, 알림 등록·탭 처리를 실제로 연결한다.
- iPhone의 홈 인디케이터, 키보드, 작은 화면, 화면 회전 및 시스템 글자 크기를 확인한다. Android 뒤로 가기 처리를 iOS에 억지로 적용하지 않는다.
- 기존 Xcode 프로젝트의 iOS 15.0 설정은 Capacitor 8 및 사용 SDK의 실제 지원 범위와 대조한다. 호환성 확인 없이 지원 OS를 광고하지 않는다.
- Windows에서 가능한 공통 코드·정적 설정 검증과 Mac/Xcode에서 하는 iOS 빌드·서명·시뮬레이터 검증을 분리한다.
- iOS 전달 완료 기준은 서명된 빌드가 App Store Connect에 정상 처리되고, 대상 테스터가 TestFlight로 설치한 뒤 로그인·동기화·푸시를 확인하는 것이다. `.ipa` 파일을 만들었다는 것만으로 일반 사용자 설치 가능이라고 하지 않는다.
- TestFlight 외부 테스터용 첫 빌드는 Apple 검토가 필요하다. 모집 후보를 App Store Connect 팀원으로 추가해 내부 테스트 제한을 우회하지 않는다.
- 사용 가능한 Mac, 유료 Apple Developer 계정, App Store Connect 권한, APNs 키 유무를 먼저 확인한다. 신규 결제·팀 초대·키 생성·외부 배포는 임의 실행하지 않는다.

## 7. 범위에서 제외할 것

- App Store·Google Play 정식 공개 출시
- 크몽·숨고·재능넷·재능아지트의 주문 자동 수집
- 새로운 결제·요금제·세금 또는 증빙 기능
- 전면적인 웹 UI 개편과 무관한 리팩터링
- 새 마케팅 분석 SDK, 광고 SDK, 베타 초대 자동 발송
- 운영 계정·기존 일감의 임의 삭제, 동의 없는 테스트 데이터 혼합

## 8. 검증과 전달 기준

구현 전 테스트를 작성하고 실패를 확인한 뒤 작은 단위로 고친다. 테스트를 건너뛰거나 검증 스크립트 문구만으로 완료를 선언하지 않는다.

| 검증 | 통과 기준 |
| --- | --- |
| 기존 웹 회귀 | 관련 단위·통합 테스트, 타입 검사, 린트, 웹 빌드 통과 |
| Google 로그인 | 외부 브라우저 → 앱 복귀 → 기존 계정 일감 조회. 취소·만료·반복 callback 안전 처리 |
| 계정 격리 | 다른 계정·로그아웃 상태에서 이전 데이터와 알림 연결을 사용할 수 없음 |
| 양방향 저장 | 앱 생성 → 웹 조회, 웹 수정 → 앱 조회, 동시 수정 충돌을 재현하고 데이터 보존 확인 |
| 수정 요청 | 동일 요청 재전송·연속 탭·푸시 중복에도 수정 횟수 한 번 반영 |
| 복구 | 오프라인·저장 실패·앱 재개·토큰 갱신 후 일관된 상태 복구 |
| 푸시 | 허용·거절·토큰 갱신·다중 기기·계정 전환·백그라운드 수신·누른 후 정확한 일감 이동 |
| Android UX | 키보드·시스템 뒤로 가기·화면 크기·탭 영역·스크롤·안전 영역을 실제 렌더로 확인 |
| iPhone UX·인증 | 홈 인디케이터·키보드·글자 크기·Scene 복귀·Keychain·로그인 취소를 실제 iOS에서 확인 |
| 설치 파일 | APK 생성, 서명·패키지 ID·버전·해시 확인, 에뮬레이터 설치와 시작 확인 |
| iOS 빌드·배포 | Mac/Xcode 빌드·서명, App Store Connect 처리, TestFlight 설치 가능 여부를 각각 확인 |
| 사용자 휴대폰 | Android·iPhone 각각 설치·Google 로그인 후 같은 일감과 요청 알림을 확인 |

검사 로그, 화면 증거, APK SHA-256, 설치 안내를 D 드라이브 프로젝트 안에 보관한다. 에뮬레이터 통과와 사용자 휴대폰 통과를 구분한다.

Android 전달 파일은 `일감체크-Android-테스트.apk`와 짧은 설치·검증 안내다. iOS는 TestFlight 설치 안내와 실제 배포 상태를 전달한다. 테스트 서명과 이후 스토어 서명이 다르면 Android는 업데이트 설치 대신 재설치가 필요할 수 있으므로 서명 방식을 전달 시 명시한다. 기존 APK와 서명키가 있는지 먼저 확인하고 임의로 교체하지 않는다.

## 9. 구현 순서와 승인 경계

1. 이 서면 설계를 검토한다.
2. 승인된 설계를 바탕으로 파일별 구현 계획·테스트 순서·실행 방식을 작성한다.
3. 최신 main 기반에서 기존 문서 변경을 보존하고 구현한다. 로컬 검증 → 독립 리뷰 → Android·iOS 빌드 순으로 진행한다.
4. Auth redirect·FCM·서버 함수·DB 마이그레이션 중 실제 외부 설정이 필요한 부분은 정확한 변경안을 제시한다. 과거 PR 배포 승인으로 새 범위를 승인받았다고 해석하지 않는다.
5. APK와 TestFlight 설치 경로를 각각 검증하고 휴대폰 설치·로그인·알림 수신을 확인한다. 정식 스토어 출시는 후속 단계다.
